About the project

Yukti answers the challenge “MeruCode” (CSE-03, Intermediate): create a program inspired by the binary patterns and combinatorial arrangements in Pingala’s Chhandas-Shastra.

The challenge

Define an encoding scheme, rebuild the input exactly, compare storage size and run time with a simple baseline, and show whether it compresses or only encodes.

The deliverable

An interactive pattern generator and encoder/decoder, with correctness tests and comparison results.

The heritage

Pingala’s prosody and the Meru Prastara. The method here is the team’s own, never claimed as a historical compression system.

Our answer

A lossless (k, rank) block codec, a Flask API, this web app, 82 tests and an honest benchmark against raw bits and zlib.

What you can do

Everything runs in the browser, and the Python backend adds the API and the zlib baseline.

Three ideas from Pingala

L (laghu) is 0 and G (guru) is 1. These three old ideas become a working encoder and decoder.

1

Prastara

List every pattern of n syllables in a fixed order. For 3 syllables that is 2³ = 8 patterns, from LLL to GGG.

2

Meru Prastara

The triangle where each number is the sum of the two above it. Row n, place k tells how many patterns have k gurus: C(n, k).

3

Uddishta and Nashta

Uddishta turns a pattern into its rank (encode). Nashta turns the rank back into the pattern (decode). Nothing is lost.

From a word to Yukti and back

The whole journey for “saket”, step by step. Nothing is lost on the way back.

What this means. The scheme is lossless and every decode matches the input. It shrinks data that is mostly zeros or mostly ones, because those blocks fall into small groups. It does not shrink normal text, and a standard compressor such as zlib usually does better. We show this openly because the challenge asks for it.

How it is built

Backend

Python 3 and Flask. core.py holds the codec, bench.py compares size and time, app.py serves the API.

Frontend

One HTML page with plain JavaScript and three.js for the 3D triangle. The codec is also written in JavaScript, so it works offline.

Testing

82 Python tests and 14 browser tests. JavaScript and Python give identical output for the same input and seed.

Repeatable data

Test data comes from the seeded Mulberry32 generator, so every comparison can be run again exactly.

The bit format

length · 32n · 8krankkrank…

The 40-bit header holds the input length and the block size n. Each block then stores k in bit_length(n) bits and rank in bit_length(C(n,k) − 1) bits. A block saves space only when k is close to 0 or to n.

Limits and questions

What Yukti does not do well, and the answers people ask most.

  • The 40-bit header is heavy for very short inputs.
  • k always costs the same bits, even for all-zero blocks, so “All zeros” is far larger than zlib’s result.
  • Very regular data such as 0101… is not shrunk, because every block has k = n/2.
  • One block size is used per stream, and the Flask server is for development.
Does Yukti compress text?

No. Short text grows (“saket” goes from 40 to 92 bits). Yukti only compresses data that is mostly zeros or mostly ones.

Did Pingala invent this method?

No. Pingala described the patterns and the Meru Prastara. The (k, rank) codec is this team’s own implementation, inspired by them.

Is decoding exact?

Yes. The codec is lossless. Every encode is checked by decoding it again, and the tests cover random inputs, Unicode text, empty input and corrupt streams.

Why does zlib often win?

zlib is a general-purpose compressor that finds repeats. Yukti only uses how many ones a block has, so it cannot see other structure.

Encode. Decode. Stay honest.

Yukti shrinks skewed data and says plainly when it cannot. That honesty is part of the design.
